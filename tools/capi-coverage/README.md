# DuckDB C API coverage across clients

Builds a dataset of which of `duckdb.h`'s `DUCKDB_C_API` functions each C-API-based DuckDB
client exposes, measured against `bindings/libduckdb/duckdb.h` in this repo as the source of
truth (currently DuckDB 1.5.5, **546** functions, 48 of them deprecated).

```bash
python3 tools/capi-coverage/fetch_clients.py     # shallow-clone the other five clients
python3 tools/capi-coverage/build_coverage.py    # writes capi_coverage.{csv,json}
```

`fetch_clients.py` is safe to re-run: it updates existing checkouts in place. The `clients/`
checkout and `capi_coverage.json` are gitignored; `capi_coverage.csv` is left trackable so that
committing it turns each DuckDB upgrade into a reviewable coverage diff. Ignore it too if that
churn isn't wanted.

## The two coverage signals

Every row carries two booleans per client, because a single "exposed?" column would be
misleading — the six clients don't share an architecture:

- **`<client>_binding`** — a publicly reachable 1:1 binding for this exact C API function
- **`<client>_wrapper`** — the function is reached from the client's idiomatic/high-level layer

| Camp | Clients | Which signal means anything |
|---|---|---|
| Hand-written, selective binding layer | Node Neo, Go, C# | **`binding`** — the apples-to-apples comparison |
| Auto-generated, exhaustive binding layer | Rust (`libduckdb-sys` bindgen), Julia (`src/api.jl`, generated by its `scripts/julia_adapter.py`) | `binding` is 546/546 by construction and carries no information; only **`wrapper`** discriminates |
| No public raw C layer | Swift — `Cduckdb` is an internal target, not a `Package.swift` product | `binding` is 0 by definition, not by omission; only **`wrapper`** exists |

Note that support tier does *not* predict which camp a client is in: C# is secondary-tier but
one of the three directly comparable clients, while tertiary Julia is trivially at 100%.

## Per-client detection

| Client | Source | `binding` | `wrapper` |
|---|---|---|---|
| Node Neo | this repo | block parse of the `// DUCKDB_C_API …` accounting comments in `duckdb_node_bindings.cpp` and `duckdb.d.ts` | `duckdb.<name>(` calls plus `export {…} from '@duckdb/node-bindings'` re-exports in `api/src` |
| Go | `duckdb/duckdb-go-bindings` (raw, a separate repo) + `duckdb/duckdb-go` (driver) | `C.duckdb_x(` inside an exported Go func | binding func re-exported by `duckdb-go/mapping` *and* used as `mapping.X` in the driver |
| Rust | `duckdb/duckdb-rs`: `crates/libduckdb-sys` + `crates/duckdb` | `pub fn duckdb_x(` in `bindgen_bundled_version*.rs` | `duckdb_x(` in `crates/duckdb` |
| C# | `Giorgi/DuckDB.NET`: `DuckDB.NET.Bindings` + `DuckDB.NET.Data` | `EntryPoint = "duckdb_x"` on `[LibraryImport]` | managed method name referenced in `DuckDB.NET.Data` |
| Swift | `duckdb/duckdb-swift`: `Sources/DuckDB` | n/a | `duckdb_x(` in `Sources/DuckDB` |
| Julia | `duckdb/DuckDB.jl`: `src/api.jl` + rest of `src` | `ccall((:duckdb_x, libduckdb)` in `api.jl` | `duckdb_x(` elsewhere in `src` |

All matches are intersected against the canonical list. This is load-bearing for Go and Rust,
where `C.duckdb_database(x)` / `duckdb_logical_type(x)` are type conversions that look exactly
like calls — no C API function name collides with a `duckdb_*` typedef, so the filter is exact.

## Reasons for non-exposure

Only Node Neo records these, and it records one for **all** of its unexposed functions.
`duckdb_node_bindings.cpp` is the richer of the two accounting files — the `.d.ts` omits
deprecation markers. Three kinds:

| Kind | Examples |
|---|---|
| `deprecated` | deprecated by the C API |
| `TODO: <area>` | `TODO: copy function`, `TODO: file system`, `TODO: aggregate function` |
| intentional | `destroyed in finalizer`, `consolidated into open`, `JS string includes length`, `no-op` |

The other five clients have no equivalent convention, so their `_reason` columns are empty. The
only reason derivable for them is structural: the `deprecated_in_c_api` column applies to all.
Go's binding layer does carry per-function `// Deprecated: Use X.` doc comments, which could be
harvested as a partial equivalent.

`node_neo.py` also has a `consistency_report()` that reports any function missing from either
Node Neo accounting file, or where the two disagree on exposure — currently zero of each. Run
`python3 tools/capi-coverage/node_neo.py` to check.

## Limitations

- C# `wrapper` matches on managed method *name*, and overloads collapse distinct C functions
  onto one name (`duckdb_open` and `duckdb_open_ext` are both `Startup.DuckDBOpen`), so it
  slightly over-reports for those.
- `wrapper` detection is textual; a function reached only via a macro or generated shim is missed.
- Each client tracks its own DuckDB version, so some gaps are just lag rather than choices. At
  the time of writing C# was on 1.5.3, and Julia's `api.jl` was generated against 1.5.4 (it
  carries two symbols, `duckdb_create_timestamp_tz_ns` and `duckdb_get_timestamp_tz_ns`, that
  aren't in 1.5.5).
